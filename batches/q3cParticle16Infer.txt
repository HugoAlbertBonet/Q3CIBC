# particle 16D — does q3c's current recipe do better WITHOUT its Langevin chain?
#
# Submit with:  bash submit_experiments.sh batches/q3cParticle16Infer.txt
# Prereq:       uv sync --extra libero --extra pushing   (particle needs neither,
#               but syncing one extra prunes the other, so sync both once)
#
# ── The question ──────────────────────────────────────────────────────────
# q3c's particle 16D numbers were all produced with inference_langevin_iterations
# = 300: 300 gradient steps on the chosen control point, per env step. That is a
# large inference cost, and on this task it is not obviously buying anything —
# the three q3cParticle seeds came out 84.0 / 0.0 / 92.0, a spread that no
# refinement setting can explain and that a 300-step chain on a narrow Q surface
# could plausibly be causing. DP at the same dimension is 71.0 +/- 7.1 with no
# refinement at all.
#
# So: same recipe, same seeds, four inference rules.
#
#   argmax   rank the 30 control points, take the best. Nothing else.
#   dfo3     3 rounds of IBC-style category-ordered resample + jitter
#   dfo10    10 rounds of the same
#   lv300    the current setting, included as the CONTROL so the comparison is
#            against a number produced by THIS batch rather than against a
#            historical run whose config.json has since changed
#
# ── Why every knob is written out ─────────────────────────────────────────
# The parameters below are read off the resolved `params` of trial
# 20260902T215321_2610192f (the 92.0 seed), NOT off batches/q3cParticle.txt.
# Most of them — separation_weight, generator_infonce_weight, the noisy-expert
# schedule, the whole langevin_* block, and inference_langevin_iterations itself
# — were never in that batch file; they came from config.json defaults. config
# .json has since changed (inference_langevin_iterations is 0 there now), so a
# line that left them implicit would train and evaluate a different policy than
# the one whose numbers this is trying to beat. Everything is therefore pinned.
#
# Reminder: apply_params_to_config SILENTLY DROPS keys not in SEARCH_SPACE. All
# keys below were checked against it before this file was written.
#
# ── Why 20 jobs and not 5 ─────────────────────────────────────────────────
# inference_dfo_iterations and inference_langevin_iterations are evaluation-time
# settings, so the textbook design is: train 5 checkpoints, then re-evaluate each
# under the four rules. That needs the checkpoints to still be on disk when the
# second batch runs — which is exactly what failed for q3cLibero, where the
# checkpoint directories were gone by re-evaluation time and 40 records had to be
# quarantined. Particle training is 46 minutes a job and the 20 jobs are
# independent, so this trains each seed once per condition instead and stays
# self-contained. Same seed + same training config = same weights, so the four
# conditions are still paired seed-for-seed (up to cuDNN non-determinism, which
# does not move a 300k-step MLP anywhere near the 8-point gaps at issue here).
#
# ── Read the results like this ────────────────────────────────────────────
# 5 seeds per condition. Compare argmax vs lv300 seed-by-seed, paired. If argmax
# matches or beats lv300, the 300-step chain is dead weight on this task and
# should come out of the particle recipe. If dfo3/dfo10 beat both, the refinement
# is worth keeping but the sampler is wrong. Watch the per-seed spread as closely
# as the mean: the thing that most needs explaining is a seed scoring 0.0.
#
# Reference points at n_dim=16 (50 eval episodes each):
#   q3c, lv300     84.0 / 0.0 / 92.0            (q3cParticle, 3 seeds)
#   DP DDIM-10     71.0 +/- 7.1                 (dpParticleV2, 2 seeds)
#   DP DDPM-100    67.0 +/- 7.1                 (dpParticleDDPM reeval, 2 seeds)
#   BC-MSE          3.0                         (IBC paper Fig 6, digitized)
